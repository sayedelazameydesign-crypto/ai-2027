## 1. الحقيقة المعمارية التي تُوجّه كل شيء

**أسرار Actions غير متاحة لتشغيل النظام المحلي إطلاقاً.** التوكن الآن يعيش
داخل سير العمل فقط، بينما نظام PA (المراقب، بوت الموافقات، المنفّذ) يعمل
خارج CI. لذلك:

```
                    ┌────────────────────────────────────────────┐
  أسرار Actions ──▶ │ مسار CI (حيث التوكن موجود اليوم)            │
  (WAAPI_API_TOKEN) │  • فحص الحضور/الجاهزية (قراءة فقط)          │
                    │  • بوابة أسبوعية للجاهزية                   │
                    └────────────────────────────────────────────┘
                    ┌────────────────────────────────────────────┐
  قيمة تُلصق يدوياً │ مسار التشغيل المحلي (نظام PA)               │
  في ‎.env ────────▶ │  • إشعار الموافقات عبر WhatsApp (اختياري)   │
  (نفس القيمة)      │  • أداة whatsapp.send عبر المنفّذ (تحت موافقة)│
                    └────────────────────────────────────────────┘
```

- **القيمة نفسها** تُنسخ مرة واحدة من GitHub → `‎.env` المحلي (لا تُرفع أبداً).
- أي محاولة جلب التوكن من GitHub داخل الكود = تصميم خاطئ (لا يوجد API آمن لذلك هنا).

## 2. المراحل (ترتيب تنفيذي صارم: hermetic أولاً، ثم حي)

### المرحلة 0 — تحقق قبل أي كود (يدها، ~15 دقيقة)

1. تشغيل `setup-status.yml` يدوياً → يثبت وجود التوكن وصحة `GET /instances`.
2. تأكيد حالة الاشتراك لدى waapi.app (مبلغ 10$ شهرياً — قرار مالي صريح).
3. تسجيل النتيجة كدليل: `::notice` من الماسح = الحضور مثبت، **بلا إرسال أي رسالة**.

**المخرج**: توكن حي + اشتراك مؤكَّد (أو توقّف — تُلغى بقية المراحل).

### المرحلة 1 — موصل hermetic بـstdlib فقط (بدون شبكة في الاختبارات)

**ملف جديد**: `src/connectors/waapi.py`

- `health()` → `GET /instances` (Timeout 15s، `redirect: error`، سقف 1MB،
  فحص `content-type: application/json`، قراءة محدودة في الذاكرة).
- `instance_id()` → يكتشف الـinstance الوحيد تلقائياً (نفس منطق الماسح الحالي:
  بالضبط instance واحد، معرّفه عدد صحيح ≥1) أو من متغيّر `WAAPI_INSTANCE_ID`.
- `send_text(chat_id, message)` → `POST …/send-message`، يعيد نتيجة مُهيكلة
  (`ok` / `refused_422` / `http_<code>` / `shape_invalid`) بلا طباعة الجسم أبداً.
- التوكن من البيئة `WAAPI_API_TOKEN`؛ **غيابه = رفض مُهيكل** (`waapi_token_missing`)
  لا استثناء ولا شبكة.
- لا سجل (log) للتوكن ولا لجسم الرد ولا لخطأ المزوّد الخام — مطابقاً لقواعد
  الماسح الحالي (`test-waapi-contact-status.js`).

**اختبار جديد**: `tests/test_waapi_connector.py` — hermetic بالكامل (ردود
مزيفة: 422، HTML، أكثر من 1MB، شكل خاطئ، توكن غائب، instance غير `ready`)…
مطابق لأسلوب الاختبارات الحالي في المستودع (HTTP قابل للحقن).

**الدليل**: `python -m unittest tests.test_waapi_connector` → OK بلا شبكة.

### المرحلة 2 — بوابة الحوكمة (الأداة تحت موافقة)

**ملفات**: `src/executors/governed_executor.py` (بلا تغيير في عقده — التسجيل فقط) +
نقطة تسجيل الأدوات + `tests/test_governed_executor.py`.

- تسجيل أداة `whatsapp.send` عبر `executor.register_tool("whatsapp.send", …)`
  — **التنفيذ يتطلب موافقة**: الحالة الافتراضية `pending` حتى تصوّت الموافقة،
  والصفوف الممنوحة حالياً (`gmail.send`, `calendar.create_event`,
  `agent.act_as_user`) **لا تشمل** `whatsapp.send` ⇒ البوابة الرابعة
  `action_not_allowed` ترفضه حتى تُضاف صراحةً.
- أسباب رفض منظّمة: `waapi_token_missing`، `waapi_instance_not_ready`،
  `assertion_*` (الظرف الموقّع من ADR-0006)، `action_not_allowed`.
- كل محاولة — نجحت أو رُفضت — تُقيَّد في سلسلة التدقيق `prev_hash → self_hash`
  (عقد المنفّذ الحالي كما هو).

**اختبارات**: أداة مزيفة عبر حقن HTTP (لا شبكة) →
(أ) بلا موافقة = `pending`/رفض، (ب) بموافقة مُستهلكة + موصل مزيف = تنفيذ
واستهلاك ذري، (ج) توكن غائب = رفض منظّم قبل أي شبكة.

### المرحلة 3 — مسار الإشعار (القيمة الفورية للربط)

**ملف**: `src/watchers/approval_bot.py` (جانب الإرسال) + `scripts/live_smoke_runner.py`.

- عند إرسال بطاقة الموافقة عبر Telegram، يُضاف **إشعار WhatsApp اختياري
  موازٍ**: نص قصير عربي + **رابط تصويت passkey** من ADR-0006
  (`PA_APPROVAL_VOTE_BASE_URL?approval=…&action=…&hash=…`).
- التفعيل بشروط تراكمية، وكلها fail-closed:
  `PA_WAAPI_NOTIFY=1` + توكن موجود + instance `ready` + وجود رابط تصويت.
- **المُستلم ثابت ومحدود**: رقم المالك (من `clinic.json developerPhone`
  بعد التطبيع المصري `201x…`) — لا يُقبل أي رقم آخر في مسار الإشعار أبداً.
- أي فشل = سطر منظّم `waapi_notify_skipped:<reason>` (بلا توكن/بلا جسم)
  واستمرار حلقة البوت — الإشعار فرع تابع، لا كسر للبوابة الأساسية.
- النتيجة تُسجَّل كأدلة في تشغيل `--send-card` للمُدخِن.

**اختبارات**: مزوّد إشعار مزيف؛ التوكن الغائب لا يُرسل ولا يُسقط؛
المستلم غير المعتمَد لا يصل إلى الشبكة.

### المرحلة 4 — اختبار حي واحد (دليل، يدوي، اختياري)

- سكربت يدوي جديد `scripts/waapi_live_smoke.py` يستدعي **نفس** `send_text`
  من الموصل: رسالة واحدة فقط إلى رقم المالك، بتشغيل `python` محلي (بلا CI).
- الإخراج: `SENT` أو `FAILED(<stage>)` — **لا جسم رد ولا توكن**.
- تطابق الماسح الحالي: وضع الافتراضي معطّل؛ بلا `--i-understand` لا شيء يُرسل.
- **الدليل**: وصول الرسالة على هاتف المالك + سطر النجاح في الطرفية.

### المرحلة 5 — التسجيل والتشغيل المستمر

1. **الجذر (شرط `scripts.test_doctor`)**:
   - `‎.env.example` قسم جديد `# --- 10. WAAPI notifications (opt-in) ---`
     بمتغيّرات `WAAPI_API_TOKEN` (فارغ)، `WAAPI_INSTANCE_ID` (اختياري)،
     `PA_WAAPI_NOTIFY=0`.
   - صفوف في `docs/SECRETS.md` (بدونها يفشل الاختبار — درس مُجرب).
2. **dr.mukhtar (شرط `setup-github.js`)**: تحديث `docs/secrets-manifest.json`
   (`used_by`, `scope`, `notes`) وصف `docs/secrets.md` لتعكس الاستعمال الجديد
   — وإلا يبقى الوصف صادقاً عن زمن مضى.
3. بوابة أسبوعية (توسعة `setup-status.yml` cron): `ready`/`NOT_READY` — قراءة فقط.
4. تدوير التوكن كل 90 يوماً: **معاً** في Actions Secret و‎.Local `.env`
   (سجل التدوير في البيان `rotation_days: 90`).

## 4. ما لن يُفعل (حدود صريحة)

- لا يُنسخ التوكن إلى Git أو الشات أو السجلات أو أخطاء المزوّد الخام.
- لا إرسال تلقائي من المراقبات؛ لا إرسال لرقم غير المالك في مسار الإشعار.
- لا اعتماد جديد على `requirements.txt` (ADR-0002: urllib فقط).
- لا webhook/رسائل واردة في هذه الخطة (مسار لاحق مستقل).
- لا تعديل لعقد المنفّذ الأربعة — التسجيل والأسباب فقط.
- لا رسائل من CI على PR (التوكن لا يُعرَض لمسارات غير موثوقة).
