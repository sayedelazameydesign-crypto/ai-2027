## What runs where

```
YCloud ──HTTPS──▶ Edge Function ycloud-webhook (Deno, verify_jwt=false; HMAC is the auth)
                    │  verify YCloud-Signature t=,s= (±300 s) / X-Hub-Signature-256
                    │  parse → 24 h window → ai2027_stage_inbound()  ← advisory lock:
                    │        duplicate check + daily cap (10) + reservation, ONE transaction
                    │  reply draft → sha256 (byte-identical to Python compute_sha256)
                    ▼  ai2027_finalize_reply() → status pending_approval   (nothing is SENT)
                 Postgres 17 (RLS on every table, no policies; RPCs = service_role only)
                    ▲
pg_cron */5 ──▶ ai2027_watchdog_tick()
                    1 cron_alive       the tick ran
                    2 edge_healthz     result of the previous tick's pg_net probe of the
                                       PUBLIC URL (gateway → Edge → PostgREST → DB);
                                       no response yet ⇒ skip (never pass)
                    3 chain_verified   full recomputation of the hash chain
                    4 inbox_integrity  no row stuck 'reserved' > 2 min; every staged
                                       reply carries a sha256 payload hash
                 → append to public.watchdog_runs (append-only; row_hash covers prev_hash)
GitHub Actions watchdog-24x7 (*/10, best-effort) ──▶ /healthz + unsigned POST must be 401
```

`verdict = pass` only when every check executed and passed; any failure ⇒ `fail`;
otherwise ⇒ `degraded`. `coverage` is stored as "N of M executed".

   `whatsapp.inbound_message.received`. Copy the signing secret YCloud shows.
2. **Supabase → Project `ai-2027-24x7` → Edge Functions → Secrets** → set
   `YCLOUD_WEBHOOK_SECRET` to that value. The current value is a **temporary test

   delivery is (correctly) refused with 401.
3. Optional: GitHub → Settings → Variables → `AI2027_WEBHOOK_PUBLIC_URL` (the
   workflow already falls back to the URL above).

## Limits — stated plainly

* **Free-plan pausing.** Supabase pauses Free projects after ~7 days of *low* activity;
  its guidance is that a few database requests a day is normally enough, but it is
  not a guarantee. This stack generates real gateway → Edge → DB requests every
  5 minutes (pg_cron probe) plus GitHub's probe. If it is ever paused, the owner
  gets an email first; "Restore" in the dashboard brings it back with data intact.
* **pg_cron/pg_net run inside the same project.** If the whole project is down, the
  in-DB watchdog is down with it — that is what the GitHub probe (outside) is for.
* **GitHub cron is best-effort** and runs only from `main`.
* **Free quotas**: 500 MB DB, 500 k Edge invocations/month. The watchdogs add ~8.6 k
  invocations (pg_cron) + ~8.6 k (GitHub, 2 calls per run) and ~4.5 MB of log per month.
* **No automatic backups** on Free. The watchdog log can be exported any time:
  `select * from public.watchdog_runs order by id`.
* Replies are **staged only** (`pending_approval`); dispatch remains behind the
  governed approval path — `MAX_SPEND=0` is preserved.

## Secrets that live in GitHub Actions → Supabase Vault (no shared credential)

GitHub Actions secrets are write-only: no API, connector or agent can read them
back — only a workflow run sees the values. So a run carries them over itself:

1. **Actions → "Sync webhook secrets to Supabase Vault" → Run workflow** (on `main`).
2. The run asks GitHub for an OIDC token (audience `ai2027-supabase-import`) and
   POSTs the allowlisted values once to `…/ycloud-webhook/import-secrets`.
3. Edge function v4 verifies the token against GitHub's live JWKS and accepts it
   only for repo id `1460619599`, owner id `233639223`, `refs/heads/main`,
   `.github/workflows/supabase-secret-sync.yml`, `workflow_dispatch`; the `jti`
   is burned in the same transaction (no replay).
4. Values go to **Supabase Vault** (`ai2027/<NAME>`, encrypted at rest); only
   SHA-256 digests come back. The script compares them, then probes the live
   webhook: signed → 200, forged → 401. Job summary shows the table; values are
   never printed.

Allowlist (anything else is refused): `YCLOUD_WEBHOOK_SECRET`,
`WHATSAPP_CLOUD_APP_SECRET`, `WHATSAPP_CLOUD_VERIFY_TOKEN`, `AI2027_WHATSAPP_WEBHOOK`.
Vault wins over Edge env for those names (refreshed ≤60 s); a Vault read error
is a 503 (YCloud retries) — never a silent fallback.

Verified against production (v4) before any workflow existed: no token → 401;
alg `none` → 401 `bad_alg`; unknown key id → 401 `unknown_kid` (proves the live
JWKS fetch); forged token with a **real** GitHub key id → 401 `bad_signature`;
Vault rows 0, burned jti 0 afterwards. DB functions are `SECURITY DEFINER`,
`search_path=''`, executable by `service_role` only.

**YCloud tip:** a YCloud signing secret belongs to the endpoint. Editing the
*existing* endpoint's URL to the Supabase one keeps the secret that is already in
GitHub; creating a new endpoint issues a new secret (put it in GitHub, re-run).
