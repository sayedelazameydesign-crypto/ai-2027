## 2️⃣ ما الذي أُضيف في هذه الجلسة بالضبط (ولماذا)

المحرّك الوحيد الغائب تمامًا في تدقيق المستودع كان **`agent-fleet`**. وقد بُني الآن كوحدة مستقلة صفرية الاعتماديات: `fleet-2027/`.

### 2.1 البنية

```
fleet-2027/
├── fleet2027/
│   ├── contracts.py   ← عقود صارمة: DAG، خطوات، نتائج، أدلة (ترفض الحقول المجهولة)
│   ├── store.py       ← SQLite WAL+FULL: مهام، خطوات، محاولات، DLQ، آثار، checkpoints، سلسلة تدقيق
│   ├── runner.py      ← موجات متوازية، مهل، heartbeat، فشل مغلق، تسليم
│   ├── registry.py    ← تسجيل الوكلاء + قدرات + circuit breaker + bulkhead + بدائل
│   ├── verifier.py    ← تحقق مستقل: بصمة الملف **من القرص** لا من كلام الوكيل
│   ├── examples.py    ← 7 وكلاء حتميين حقيقيين (ملفات + compile + probe)
│   └── __init__.py
├── tests/             ← 101 اختبارًا، منها اختبار SIGKILL حقيقي
├── cli.py             ← demo / plan / run / recover / status / verify / dlq / export / import / cancel
├── crash_worker.py    ← عامل خارج العملية يُقتل فعلًا في البوابة
└── gate.py            ← 9 بوابات تُنتج launch/evidence/fleet-2027-gate.json
```

### 2.2 الآليات العشر للاعتمادية — وأين كل واحدة بالكود

| الآلية | كيف نُفّذت | كيف تُكذّب | البوابة |
|---|---|---|---|
| **Checkpointing** | كل خطوة تكتب نتيجتها + بصمتها قبل الانتقال | اقتل العملية في منتصف خطوة | `sigkill-resume` |
| **Durable Queue / State** | حالة المهمة والخطوات في SQLite، لا في الذاكرة | أعد تشغيل العملية ← الحالة موجودة | `sigkill-resume` |
| **Atomic Claiming** | `BEGIN IMMEDIATE` + UPDATE مُتحقَّق العدد | عاملان يتسابقان ← فائز واحد | `test_two_concurrent_workers_cannot_both_claim_a_step` |
| **Lease + Heartbeat** | خيط منفصل يجدّد الإيجار أثناء خطوة طويلة | إيقاف الخيط ← استعادة الإيجار | `test_expired_leases_are_requeued_with_the_attempt_recorded` |
| **Retry with Backoff** | `next_attempt_at` محسوب، والمدير **ينتظر** لا يلفّ | تجاوز الـbackoff | `retry-backoff` |
| **Idempotency** | جدول `effects` بمفتاح حتمي `sha256(task::step)` | إعادة تشغيل الخطوة ← `fresh=False` | `idempotency` |
| **Circuit Breaker** | عدّاد فشل لكل وكيل + مهلة تبريد | وكيل ميت ← خروج من السلسلة | `test_a_fallback_is_used_when_the_primary_breaker_is_open` |
| **Bulkhead** | بركة رموز لكل وكيل بـ`max_parallel` | وكيل بطيء ← لا يستهلك الخيط | `test_capacity_is_bounded_and_returned` |
| **Dead Letter Queue** | جدول `dead_letters` + `requeue` بميزانية جديدة | استنفاد المحاولات ← تُرحَّل | `dead-letter` |
| **Graceful Degradation** | خطوة `critical=False` تفشل ← المهمة `succeeded`+`degraded` | حذف وسم degradation | `degraded-success` |

### 2.3 التحقق المستقل — جوهر الفرق عن «طاعة الوكيل»

```
الوكيل يقول:  ok=True, artifacts=[report.md sha256=abc…]
الـverifier:  افتح report.md من القرص، أعد حساب sha256، قارن.

إن اختلفا ← الخطوة فاشلة ⇒ إعادة محاولة ⇒ ثم DLQ.
              ولا تُسجَّل أبدًا كـ»منجزة«.
```

**قاعدة مثبتة في CI:** `scripts/fleet_guard.py doctest` يفشل إذا ظهر في `runner.py` أي مسار يكتب نجاحًا بلا `verify_step`. أي أن «التصديق الذاتي» ممنوع بنيويًا لا بالانضباط.

### 2.4 نتيجة البوابة (مقيسة اليوم، لا مُدَّعاة)

```
PASS parallel-wave     · PASS verification-refuses · PASS retry-backoff
PASS dead-letter       · PASS degraded-success    · PASS failover
PASS idempotency       · PASS audit-chain         · PASS sigkill-resume
9/9 · artifact = launch/evidence/fleet-2027-gate.json
```

والبوابة الأخطر تفصيلها:

| ما حدث فعلًا | القيمة المقيسة |
|---|---|
| عامل أُطلق في عملية منفصلة | `pid` مكتوب، ثم `kill -9` |
| رمز خروج العامل | **−9** (SIGKILL، لا تنظيف) |
| حالة الخطوة أثناء التنفيذ | `running` بإيجار بائت |
| العمل المُنجز قبل القتل | `first = succeeded` **لم يُفقد** |
| استئناف من عملية **جديدة** | أرقام المحاولات `[1, 2]` — المحاولة الضائعة مُسجَّلة |
| الأثر الجانبي | سطران في السجل، **`fresh_effect=true` مرة واحدة فقط** |
| سلسلة التدقيق بعد الاستئناف | `integrity ok = True` |

## 5️⃣ ما لا يجب فعله (مستخلص من هذه الجلسة بالدليل)

| الخطأ | ما يحدث فعلًا | ما فعله هذا المستودع |
|---|---|---|
| تصديق `ok=True` | خطوة «ناجحة» بلا ملف على القرص | الـverifier يعيد حساب البصمة؛ `doctest` يمنع المسار |
| مسح مسار خطأ بـ`except: pass` | فشل صامت | `fleet_guard.py` يفشل على `except …: pass` |
| `executescript` داخل معاملة | `cannot commit - no transaction is active` | فصلناه وعلّقنا السبب في الكود |
| إعادة الخطوة لحالتها «البدائية» عند الفشل | تقدم مفقود | `attempts` تُسجَّل قبل التنفيذ، و`lost_lease` تُكتب |
| الاعتماعلى خيط واحد لكل شيء | وكيل بطيء يوقف الأسطول | bulkhead لكل وكيل + مهل لكل خطوة |
| «الاختبار يُثبت الجودة» | اختبار يمرّ على محاكاة | البوابة تقتل عملية حقيقية وتقيس الأثر |

## 6️⃣ الحد الصادق لما أنجزناه

**نعم، أُنجز:**
محرّك مهام دائم، مسارات استئناف مُثبتة بقتل عملية، تحقق مستقل يرفض الكذب، DLQ، idempotency، circuit breaker، bulkhead، سلسلة تدقيق، 101 اختبارًا، 9 بوابات، CLI كامل، حارس CI، وتحديث مصدر حقيقة التدقيق من `absent` إلى `partial`.

**لا، لم يُنجز بعد:**
- لا يوجد **وكيل LLM** داخل الـfleet (الوكلاء الحاليون برامج حتمية — وهذا مذكور في مخرجات CLI نفسها).
- لا يوجد **توزيع عبر عُقد** (threads داخل عملية واحدة).
- **MCP**، **متصفح حقيقي في CI**، **xlsx/pptx**، **نشر حي** — كلها لاحقة بترتيبها في جدول PRs.

**الحد الأدنى للإطلاق التنافسي (15/15 في خريطة المستخدم) لا يزال بعيدًا:** 9 من 15 مكوّنًا منفّذ جزئيًا على الأقل، 0 منها «مكتمل بمعيار منتج تجاري». هذا الرقم الصادق أهم من أي شعار.

## 9️⃣ A1 — وكيل LLM حقيقي (منفّذ)

### المبدأ الذي لم يُخترَق

> **مخرجات النموذج ادّعاء، لا نتيجة.** النموذج يكتب الملف، ثم **الـverifier** يعيد حساب بصمته من القرص ويقرر.
> ولا يوجد مسار واحد يقول «النموذج قال إنه نجح».

### البنية

```
LLMAgent.handler(ctx)
   ├─ يبني LLMRequest (حدود صارمة: ≤16k حرف، ≤4k توكنز، ≤300 ثانية)
   ├─ backend.complete()  ← واجهة Protocol واحدة، بلا أي SDK داخل الحزمة
   ├─ يستخرج كتلة الكود (```python … ```) أو يرفض الردود الاعتذارية
   ├─ يكتب الملف داخل الـworkspace فقط (رفض `../` قبل استدعاء النموذج أصلًا)
   └─ يعيد StepResult تحمل ArtifactRef بمسار نسبي + بصمة حقيقية
          ↓
   verifier.verify_step()  ← إعادة حساب البصمة من القرص
          ↓ نجاح: record_success · فشل: retry ← ثم DLQ
```

### الخلفيات (Backends) — كلها قابلة للحقن

| الخلفية | الاستخدام | الحد الأمني |
|---|---|---|
| `OllamaBackend` | الافتراضي · Free-First · صفر تكلفة | HTTP عادي مسموح **لـloopback فقط** |

## 🔟 A3 — عدة عمليات على قاعدة واحدة (منفّذ)

**المشكلة الحقيقية:** التأكد من أن خطوتين لا تُنفَّذان مرتين لم يكن ليُثبت داخل عملية واحدة. `threads` تشترك في الذاكرة؛ العمليات الحقيقية لا تشترك إلا في **القرص**.

| الآلية | ما تضمنه فعلًا |
|---|---|
| جدول `workers` | من حيّ، على أي مضيف/pid، وكم خطوة «احتفظ» بها العامل |
| `claim_ready_steps(capacities=…)` | الموجة لا تتجاوز `max_parallel` للوكيل؛ الزائد **يبقى في الطابور** بدل استهلاك المحاولات |
| `requeue_steps_of_dead_workers` | تُحرَّر خطوات المالك **الميّت فقط**؛ لا تُسرق lease حيّة |
| write-ahead effects | `intent` ← تنفيذ الأثر ← `complete`؛ السقوط يترك `state='intent'`، وعلى العامل الجديد أن يتحقق أو يعوّض **لا أن يكرّر** |
| `serve(idle_exit_after_s=…)` | يخرج بنفسه حين لا يبقى عمل — اختبار أو cron أو CLI كلها تنتهي |

### القياس (بوابة `multi-process`، تشغيل حقيقي)

| السيناريو | النتيجة |
|---|---|
| عاملان، 6 خطوات، وكيل متوازٍ | 6 آثار لـ6 خطوات · كل خطوة مرة واحدة · pids مختلفة في السجل |
| عاملان، وكيل `max_parallel=1` | لا حدث `bulkhead saturated` واحد · كل الخطوات من المحاولة الأولى |
| عامل يُقتل بـ`SIGKILL` بين الأثر واكتماله | المهمة `succeeded` · 4 آثار لـ4 خطوات · 0 intent غير محسوم |

### الحد الصادق لـA3

- **الحيوية heartbeat لا أوراكل.** عامل مقتول يبدو حيًّا حتى تتقادم ضربته، فزمن التعافي ≈ `--stale-after-s`.
- **ليست موزّعة عبر الآلات.** SQLite على قرص محلي تنسّق *عمليات*؛ ملف على شبكة يحتاج قفلًا يعمل، ولذلك `multi-node` غير مُنفَّذ بدل أن يُدَّعى.
- **الأثر الخارجي مسؤولية الوكيل.** المكتبة توفّر `declare_effect_intent`/`complete_effect`؛ الوكيل الذي لا يستخدمها يبقى at-least-once، ويُقال ذلك صراحةً.
