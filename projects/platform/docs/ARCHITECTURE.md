## 3. نقاط الانتباه من التحليل — وحالتنا تجاهها

| التحذير | حالتنا |
|---|---|
| لا Microservices من اليوم الأول | ✅ ملتزمون — عملية واحدة، طبقات مفصولة بالكود |
| لا يتحكم LLM في السيرفر مباشرة | ✅ النموذج يقترح خطة فقط؛ Zod + registry + بوابة موافقة بينه وبين أي تنفيذ |
| Sandbox معزول | ✅ ضمن حدود معلنة (execFile+allowlist+مجلد مقيد، بلا حاويات — موثق) |
| Streaming جوهري | ✅ SSE من اليوم الأول + كمبيوتر وكيل حي |
| فصل Control عن Execution ولو بنفس المشروع | ✅ `src/app/api` (تحكم) منفصل عن `src/agent` (تنفيذ) بحدود استيراد واضحة |

## 4. الفجوات الحقيقية المتبقية (بترتيب الاستحقاق)

1. **Auth + Users + عدّاد استخدام** (Control Plane) — الفجوة الوحيدة المانعة
   للربح (freemium يتطلب هوية). ← v3 القادمة
2. **Redaction + retry classifier + idempotency** — Phase 3 من عقد Module 2
3. **Projects** (تجميع تشغيلات في مشروع بسياق مشترك) — بعد مستخدمين فعليين
4. **Memory/RAG + Model routing متعدد** — فقط عند حاجة يثبتها الاستخدام

## 5. مسار التفكيك المستقبلي (متى نفصل الخدمات؟)

| العرض | الحل حينها |
|---|---|
| تشغيلات متزامنة تخنق العملية | فصل Agent Worker + طابور (وقتها فقط يدخل Redis/BullMQ) |
| مستخدمون يشغلون كودًا عدائيًا | Sandbox حاويات معزول لكل تشغيلة |
| قاعدة SQLite تختنق كتابةً | driver → Postgres (تغيير سطر في Drizzle) |

القاعدة الثابتة: **كل تفكيك يحتاج اختناقًا مقاسًا، لا توقعًا.**
