# Module 2 — Agent Execution Contract

## القرار المعماري

يعتمد الـMVP استراتيجية **plan-then-execute**. يكوّن الوكيل خطة كاملة ومنظمة قبل تشغيل أي أداة، ثم يتحقق منها مقابل سجل الأدوات، ومخططات المدخلات، وحد الخطوات. لا يُعاد تخطيط الخطة تلقائياً داخل المهمة نفسها في هذه النسخة؛ عند الغموض يتوقف الوكيل بحالة `needs_clarification`، وعند عدم صلاحية الخطة يتوقف بحالة `plan_rejected`.

## دورة الحالة

| الحالة | المعنى | الانتقالات المسموحة |
|---|---|---|
| `goal_submitted` | تم استلام هدف المستخدم | `planning` |
| `planning` | النموذج اللغوي يبني خطة منظمة | `plan_validated` أو `plan_rejected` أو `needs_clarification` |
| `plan_validated` | اجتازت الخطة فحوص الأدوات والمدخلات والحدود | `executing` أو `awaiting_approval` |
| `awaiting_approval` | توقفت المهمة قبل خطوة حساسة محددة | `executing` أو `cancelled` |
| `executing` | تنفيذ الخطوات بالتسلسل | `awaiting_approval` أو `retry_scheduled` أو `completed` أو `failed` أو `partially_completed` |
| `retry_scheduled` | فشل transient مع بقاء محاولات | `executing` أو `failed` أو `partially_completed` |
| `plan_rejected` | الخطة غير قابلة للتنفيذ أو مخالفة للعقد | حالة نهائية |
| `needs_clarification` | الهدف غير كافٍ لاختيار خطة آمنة | `planning` بعد توضيح المستخدم أو `cancelled` |
| `partially_completed` | نجحت خطوات سابقة وفشلت خطوة لاحقة نهائياً | حالة نهائية |

## خوارزمية التنفيذ

1. ينشئ `agent.run` مهمة بحالة `goal_submitted` ثم ينقلها إلى `planning`.
2. يطلب من النموذج اللغوي مخرجاً منظماً يطابق مخطط الخطة، ويحد الخطوات بخمس خطوات.
3. يتحقق `validatePlan` من وجود الأداة وتفعيلها وصحة بنية المدخلات. الفشل ينتج `plan_rejected`، والغموض ينتج `needs_clarification`، وكلاهما يُسجل في سجل التدقيق قبل إنشاء خطوات تنفيذية.
4. بعد التحقق، تُنشأ كل الخطوات بمفتاح idempotency ثابت مشتق من `taskId` و`stepId`.
5. تُفحص خطورة كل خطوة مباشرة قبل تشغيلها. إذا كانت حساسة، تُنشأ موافقة مرتبطة بـ`stepId` ويتوقف المسار. الخطوات الآمنة السابقة تبقى مكتملة.
6. بعد الموافقة، تستأنف الحلقة من الخطوة الحساسة نفسها ثم تتابع الخطوات اللاحقة. الرفض يحول المهمة إلى `cancelled` ولا ينفذ الأداة.
7. قبل الأثر الخارجي، ينفذ النظام claim ذرياً على جدول `tool_executions` بمفتاح idempotency. وجود نتيجة مكتملة يعيدها دون تنفيذ ثانٍ، ووجود claim غير مكتمل يمنع التنفيذ المتوازي.
8. الأخطاء التي تطابق timeout أو 429 أو 5xx أو الشبكة تُصنف `retryable`، وتنتقل الخطوة إلى `retry_scheduled` ثم `running` ضمن `maxAttempts`. الأخطاء الحتمية تنتهي مباشرة إلى `failed` أو `partially_completed` إذا وُجدت نتائج سابقة.
9. تُحفظ المدخلات والمخرجات والأخطاء والقرارات في سجل التدقيق بعد تمريرها عبر `redactSecrets`.

## حدود الأمان في الـMVP

يُحظر تنفيذ الأدوات الحساسة دون موافقة مرتبطة بالخطوة نفسها. لا تُعرض المفاتيح أو كلمات المرور أو الرموز داخل سجل التدقيق، ويُستعمل حد ثابت للخطة والمحاولات. التنفيذ داخل هذه النسخة محصور في الأدوات المسجلة والمفعلة، ولا توجد صلاحية تنفيذ أداة غير موجودة في الـregistry.
