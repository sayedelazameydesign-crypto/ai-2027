## 2. لماذا هذا القدر من الحذف؟

الـ Skill الأصلية صُممت كـ **بروتوكول توفير توكنات لواجهة دردشة** — بيئة بلا ملفات
ولا git ولا اختبارات. نظامنا يملك بالفعل: مستودعًا (Source of Truth)، بوابات
(e2e/gap-audit/tsc/build + موافقات planHash)، أثرًا دائمًا (runs.trace)، وحوكمة
(docs/governance). فكل قسم يحاكي هذه الوظائف داخل المحادثة صار **تداخل مسؤوليات**
— وهو الخطر الأكبر المحدد في المراجعة.

# SKILL v2 — Engineering Operating Layer

```yaml
name: engineering-operating-layer
version: 2.0
role: منهجية التفكير والتنفيذ الهندسي فقط
position: فوق الـ Orchestrator، تحت المالك — لا تحل محل أي طبقة قائمة
```

## الحدود السيادية (من المراجعة المعتمدة)

| الطبقة | مسؤوليتها | والـ Skill تجاهها |
|---|---|---|
| Orchestrator / Agent Core | تنسيق الوكلاء والأدوات | ❌ لا تتخذ قراراته |
| Memory Fabric | حفظ واسترجاع الحالة | ❌ لا تخزن بنفسها — تقرأ من المستودع/DB |
| Gates | السماح والمنع والتحقق | ❌ لا تتجاوزها — تستشهد بنتائجها |
| Source of Truth | GitHub origin/main + قاعدة runs | ❌ لا تخترع مصدرًا موازيًا |
| Execution Plane | تنفيذ داخل الحدود | ❌ لا تنفذ خارج sandbox/أدوات مسجلة |
| Checkpoint | حالة قابلة للاسترجاع | تلتزم به ولا تعيد تعريفه |

## القدرات الست (الحصرية)

### 1. System Discovery — الاكتشاف قبل التعديل
قبل أي تغيير: اقرأ `docs/ARCHITECTURE.md` والعقود القائمة، افحص الكود الفعلي
(`git ls-files`, `grep`) لا الذاكرة. **يُمنع إعادة بناء مكوّن موجود** — الاكتشاف
أولًا يمنع ذلك بالتصميم.

### 2. Change Impact Analysis — تحليل أثر التغيير
لكل تغيير مقترح، حدد قبل التنفيذ: الملفات المتأثرة، العقود/المخططات المتأثرة
(Zod، SSE union، جداول DB)، الاختبارات التي يجب أن تبقى خضراء، والاختبارات
الجديدة المطلوبة. تغيير بلا خريطة أثر = مرفوض.

### 3. Execution Planning — مراحل ببوابات
حوّل الهدف إلى مراحل، لكل مرحلة **شرط خروج قابل للتحقق آليًا** (اختبار، فحص،
قياس). لا مراحل بشروط خروج إنشائية («يبدو جيدًا»).

### 4. Evidence-Driven Engineering — لا اكتمال بلا دليل
المهمة تكتمل بدليل قابل للمراجعة: خرج اختبار فعلي، لقطة متصفح حقيقية، استعلام
تحقق، رد HTTP. **نجاح الكود ≠ نجاح النظام** — الدليل يكون على مستوى السلوك
المتكامل end-to-end (الواجهة ↔ الخلفية ↔ الأدوات).

### 5. Checkpoint Discipline — تثبيت الحالة
بعد كل تغيير مهم: commit ذو رسالة دالة تتضمن حالة البوابات. القوالب في
`docs/governance/templates/` للتغييرات الجسيمة. لا تراكم عمل غير مثبت عبر مراحل.

### 6. Resource & Context Management — بلا مسرحيات
- الملفات المرجعية (ARCHITECTURE، التقارير) تغني عن إعادة السرد — أشِر إليها.
- الكود والدليل أولًا؛ الشرح بقدر القرار المطلوب.
- لا تشغيل أدوات/اختبارات لا يخدم شرط خروج المرحلة الجارية.
- ممنوع: عدادات وشارات ونسب تخمينية في الردود.

## سلم الجاهزية — القفز ممنوع

```
IMPLEMENTED   الكود موجود ويُبنى (tsc + build)
    ↓
TESTED        بوابات آلية خضراء (e2e 33/33 · gap-audit)
    ↓
VERIFIED      دليل سلوكي متكامل (تشغيلة حية موثقة، لقطات، ملفات ناتجة)
    ↓
PRODUCTION-READY  أسرار مدارة · وصول خارجي · smoke tests · خطة rollback
    ↓
DEPLOYED      عملية النشر نجحت والخدمة تستجيب علنًا
    ↓
OBSERVED      صمدت تحت استخدام حقيقي + مراقبة تشغيلية + دليل استرداد مُجرَّب
```

> `DEPLOYED ≠ WORKING IN PRODUCTION` — نجاح النشر لا يثبت الصمود تحت traffic
> حقيقي. `OBSERVED` مرحلة لاحقة للنشر الأول، وليست شرطًا مانعًا له.

**تصنيف نواة الحالي بموجب السلم: `VERIFIED`** — وليس production-ready:
المتبقي للترقية: Auth/العزل، تدوير الأسرار، smoke tests على بيئة النشر،
دليل rollback. (هذا هو الرد المنهجي على مغالطة «9/10 طبقات = جاهز»).
