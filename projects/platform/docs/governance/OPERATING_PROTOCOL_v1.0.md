# Celia.Pro Operating Protocol v1.0

## 1. الغرض

يحدد هذا البروتوكول طريقة تنفيذ تغييرات Celia.Pro عبر وكيل هندسي مضبوط الصلاحيات. الهدف هو ضمان أن كل تغيير قابل للتتبع، محدود النطاق، قابل للاختبار، ولا يندمج قبل المراجعة والموافقة البشرية.

> **قاعدة حاكمة:** لا تُعد المهمة مكتملة بمجرد تعديل الكود؛ تُعد مكتملة فقط بعد اجتياز بوابات التحقق وإنتاج Evidence قابل للمراجعة.

## 2. الأدوار والصلاحيات

| الدور | المسؤولية | الصلاحيات |
|---|---|---|
| Owner / Architect / Approver | تحديد الهدف والنطاق واعتماد الخطة والنتيجة | الموافقة على التغييرات الحساسة والدمج النهائي |
| Controlled Engineering Executor | التحليل والتنفيذ والاختبار وإعداد الأدلة | العمل داخل الفرع المخصص والنطاق المعتمد فقط |
| GitHub | مصدر الحقيقة للكود والتاريخ | حفظ الفروع والـCommits والـPull Requests |
| Tests / Validation | التحقق الآلي واليدوي | قبول أو رفض نتيجة التغيير بناءً على الأدلة |

## 3. القواعد غير القابلة للتفاوض

1. لا يُعدّل الـBaseline المجمد مباشرة.
2. لا تتغير العقود العامة دون موافقة صريحة.
3. لا تتغير مخططات قاعدة البيانات دون مراجعة Migration Safety.
4. لا يُدفع مباشرة إلى `main` أو `master`.
5. لا تُحذف وظيفة قائمة إلا بطلب تغيير معتمد.
6. كل تغيير يجب أن يتضمن اختبارات مناسبة.
7. كل مهمة مكتملة يجب أن تنتج تقرير Evidence.
8. عند غموض النطاق أو اكتشاف أثر أمني أو تعاقدي غير متوقع، يتوقف التنفيذ ويُطلب اعتماد بشري.

## 4. بوابات Change Request

كل Change Request يجب أن يمر بالترتيب التالي:

```text
CR
 ↓
Baseline Verification
 ↓
Scope & Impact Analysis
 ↓
Execution Plan
 ↓
Human Approval
 ↓
Implementation
 ↓
Tests
 ↓
Failure Analysis
 ↓
Fix / Retest
 ↓
Security & Contract Review
 ↓
Evidence Report
 ↓
Checkpoint
 ↓
Pull Request
 ↓
Human Approval
 ↓
Merge
```

لا يجوز الانتقال من **Execution Plan** إلى **Implementation** في التغييرات الحساسة قبل تسجيل الموافقة البشرية.

## 5. مرحلة Baseline Verification

قبل أي تعديل، يجب تسجيل معرف الـBaseline، والـCommit، والفرع، والتاريخ، وحالة المستودع، ومناطق الحماية، والتغييرات المسموح بها. يجب أيضًا التأكد من عدم وجود تغييرات محلية غير مقصودة.

## 6. تحليل النطاق والأثر

يجب أن يحدد التحليل الملفات والمكونات المتأثرة، والعقود العامة، وأثر قاعدة البيانات، والأثر الأمني، والاختبارات المطلوبة، والمخاطر، وما هو خارج النطاق. أي ملف أو مكون خارج النطاق لا يُعدل دون تحديث واعتماد طلب التغيير.

## 7. قواعد Git

يجب تنفيذ كل CR في فرع مستقل باسم وصفي، وإنشاء Commits صغيرة قابلة للمراجعة، وعدم إعادة كتابة تاريخ الفرع المشترك. يُقترح استخدام Pull Request لكل تغيير، مع ربطه بمعرف CR وتقرير Evidence.

## 8. قواعد الاختبار

يجب تشغيل الاختبارات الموجودة ذات الصلة قبل التعديل عندما يكون ذلك ممكنًا لتثبيت خط أساس، ثم تشغيلها بعد التعديل. يجب إضافة اختبارات للسلوك الجديد أو للحالة التي عالجها التغيير، وتسجيل الأوامر والنتائج وحالات الفشل والإصلاحات.

## 9. قواعد الأمان والعقود

يجب فحص التغييرات التي تمس المصادقة، والجلسات، والصلاحيات، والبيانات الحساسة، وواجهات API، ونماذج البيانات، والتكاملات الخارجية. يجب توثيق نتيجة فحص الأمن والعقود في Evidence حتى عند عدم العثور على مشكلة.

## 10. Emergency Stop

يتوقف التنفيذ فورًا عند اكتشاف أحد الأمور التالية: توسع غير معتمد في النطاق، خطر فقدان بيانات، تغيير غير متوقع في عقد عام، فشل أمني حرج، غياب Baseline موثوق، أو فشل اختبارات لا يمكن تفسيره ضمن النطاق الحالي.

## 11. صيغة أمر التنفيذ

يجب أن يحدد كل أمر تنفيذي: معرف CR، الـBaseline، الـCommit المرجعي، النطاق، المناطق المحمية، معايير القبول، الاختبارات المطلوبة، وشروط التوقف. الصيغة العامة:

> نفّذ Change Request محددًا ضمن الـBaseline المسجل. لا تعدّل خارج النطاق. حلّل الأثر، قدّم خطة، توقف للموافقة عند الحاجة، نفّذ التغيير، شغّل الاختبارات، راجع الأمن والعقود، وأنشئ Evidence وCheckpoint قبل اقتراح Pull Request.

## 12. معيار الإكمال

تُعتبر المهمة مكتملة فقط إذا تحقق الآتي: تغييرات محددة ومراجعة، اختبارات ناجحة أو إخفاقات موثقة ومقبولة، مراجعة أمنية وتعاقدية، Evidence مكتمل، Checkpoint مسجل، وPull Request جاهز للموافقة البشرية.
